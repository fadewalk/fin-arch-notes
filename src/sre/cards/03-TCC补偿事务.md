## 一句话定位
TCC 把分布式事务搬到业务层:Try-Confirm-Cancel 每阶段都是完整提交的本地事务,Cancel 用反向业务对冲第一阶段效果,换短锁持有时间。

## 典型故障模式
- **中间态瞬时空窗**:Try 已真正提交、Confirm/Cancel 未执行 → 账面瞬时"少了钱"(如转账双方停在中间值);微观不原子的固有表现,不是丢钱。
- **Try/Cancel 乱序**:先收 Cancel 后收 Try → 没做空回滚的实现在此报错或错误执行。
- **悬挂事务**:空回滚记录没被检查,迟到 Try 又执行 → 已取消业务的正向效果"复活",无确认阶段收尾。
- **Cancel 被当回滚实现**:Try 已提交、数据库层不可回滚 → Cancel 报错或反向失败,对账出现单向差额。
- **停在中间态收不了尾**:协调者或参与方故障 → 大量事务停在 Try 后,中间态远超预期窗口。

## 观测信号
- `tcc_pending_txn_age`:Try 完成到 Confirm/Cancel 终态的时长;增长=收敛链路断。
- `empty_cancel_count`:空回滚次数;稳定存在=乱序被正常处理。
- `suspended_try_blocked_count`:防悬挂拦截迟到 Try 的次数;不拦截即悬挂事故信号。
- `tcc_compensation_lag`:补偿动作相对 Try 的延迟;抬升=协调者积压或参与方响应慢。
- `intermediate_state_diff_count`:中间态账面差额(对账口径);应随补偿完成归零。

## 应急动作
- 事务停在中间态 → 协调者按全局记录重推 Confirm/Cancel;每阶段是完整本地事务,重试安全,业务需幂等。
- Cancel 无 Try 报错 → 补齐异常三加强(允许空回滚、空回滚留记录、防悬挂)后重放该事务。
- 账面差额不归零 → 对账定位未收尾事务清单,逐单驱动补偿,再查协调者与参与方链路。

## 常见误区
- Cancel 不是数据库回滚,是反向业务对冲;每个业务必须写正反两套,少一套即事故源。
- "转账必须原子"是宏观结论,微观有可见中间态,靠最终正确收尾——别把中间态告警当资金事故硬查。
- 最复杂的异常不是宕机而是乱序:没收到 Try 却收到 Cancel,三重加强就是为它准备的。
